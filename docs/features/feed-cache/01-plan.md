# feed-cache: 목록 상태를 라우트 전환 뒤에도 유지 기획

작성일: 2026-11-11. 모델: fable. 상태: 승인됨 (2026-11-11).

## 목적

목록에서 릭 상세로 갔다가 브라우저 뒤로 가기로 돌아오면 보던 카드가 같은 자리에 그대로 있게 한다.
지금은 돌아올 때마다 첫 페이지부터 다시 받고 스크롤이 맨 위로 가서, 아래쪽 릭을 둘러보던 사람은 매번 다시 내려가야 한다.
이 목록 캐시는 다음 기능 `lick-page` 가 `/lick/:id` 를 넘기기 플레이어로 바꿀 때 플레이어가 출처 목록을 읽고 이어 붙이는 바탕이 된다.

## 근거

- `docs/features/INTAKE.md` 개정 3. 라우트 모델을 고르면서 오버레이가 피하고 있던 목록 재마운트 문제를 먼저 푼다.
- `harness/DECISIONS.md` 2026-11-11 첫 항목. 오버레이를 고른 이유가 "목록이 다시 마운트되지 않아 스크롤 위치가 남는다" 였다. 이 기능이 그 이유를 없앤다.
- `docs/features/community/design.md` 목표 절(영속 링크 `/lick/:id`, 목록은 무한 스크롤), 8.2절 카드, 8.5절 keyset 커서 무한 스크롤.
- `docs/features/swipe-play/01-plan.md` 확정된 사실 절. "라우트가 바뀌면 Feed 가 다시 마운트돼 첫 페이지부터 다시 받고 스크롤 위치를 잃는다."
- `src/community/views/Feed.tsx` FeedList(행, 좋아요 수, 커서, done, 태그 총 개수)와 바깥 Feed 의 key 리마운트.
- `src/community/Root.tsx` 라우트 switch, `src/community/routing.ts` navigate 와 useRoute, `src/community/hooks/useInfiniteScroll.ts`.

## 확정된 사실 (코드 조사와 실측)

- Root 는 라우트 이름으로 switch 해서 뷰 하나를 `<main>` 에 둔다. `/` 에서 `/lick/:id` 로 가면 Feed 가 언마운트되고 LickDetail 이 마운트된다. 돌아오면 Feed 가 새 인스턴스로 마운트된다.
- FeedList 의 행, 좋아요 수, 커서, done, 태그 총 개수는 전부 그 인스턴스의 useState 와 useRef 다. 언마운트와 함께 사라진다.
- Feed 는 네 곳에서 쓴다. Latest(`/`), 태그 피드(`/tag/:name`), 유저 페이지(`/user/:public_id`, authorId), 내 릭(`/me`, authorId 와 deletable). 바깥 Feed 는 `(authorId ?? '') + '|' + (tag ?? '')` 를 key 로 삼아 필터가 바뀌면 리마운트한다.
- 운영(2026-11-11, 폰 폭 390)에서 재 보았다. Latest 를 두 페이지(40장) 내려 scrollY 3173 에서 카드 본문을 탭하고 상세에서 뒤로 가기를 누르면, 목록 요청이 1건 다시 나가고 카드는 20장이 되며 scrollY 는 0 이다. 1.5초 뒤에도 0 이다. `history.scrollRestoration` 은 기본값 auto 이고 코드 어디에서도 바꾸지 않는다.
- 스크롤 컨테이너는 모든 폭에서 window 다. `.c-main` 과 `.community-shell` 에는 overflow 가 없다. overflow-y auto 는 검색 제안, 모바일 검색, 플레이어 페이저에만 있다.
- `navigate(path)` 는 `history.pushState(null, '', path)` 뒤에 합성 `PopStateEvent` 를 보낸다. `useRoute` 는 popstate 하나만 듣는다. 그래서 진짜 뒤로 가기와 코드 이동이 같은 핸들러에 닿고, 지금은 둘을 구분하는 표식이 없다. 표식을 둘 수 있는 자리는 셋이다. navigate 가 만드는 합성 이벤트(우리가 만들므로 state 나 detail 을 붙일 수 있다), routing.ts 의 모듈 변수, pushState 에 넣는 history.state.
- 명시적 이동은 전부 navigate 를 거친다. 탭 바 Latest, 사이드바 Latest 와 태그, 앱 바와 모바일 앱 바 로고, 로그아웃 뒤 `/`, 편집기 Exit 의 `lastCommunityPath`, 상세 삭제 뒤 `/me`, 게시 뒤 `/lick/:id`.
- Latest 에 있으면서 탭 바 Latest 를 다시 누르면 pushState 로 같은 경로가 한 번 더 쌓이고 Feed 는 같은 요소라 리마운트되지 않는다. 화면에는 아무 일도 없다.
- `useInfiniteScroll` 은 센티널이 보이면 loadMore 를 부르고 진행 중에는 다시 부르지 않는다. 센티널은 `loaded && !done` 일 때만 렌더된다.
- loadMore 는 페이지와 좋아요 수를 모두 받은 뒤에야 커서를 전진시킨다. 실패하면 커서가 그대로라 재시도가 같은 페이지를 받는다.
- 내 릭은 이름을 바꾸면 `key={renames}` 로 Feed 를 리마운트해 목록을 다시 받는다. 카드의 작성자 이름이 피드 질의에 박혀 있기 때문이다.
- 유저 페이지는 프로필 요청이 끝난 뒤에야 Feed 를 마운트한다. 내 릭은 프로필과 무관하게 Feed 를 바로 마운트한다.
- 좋아요 수의 대상은 항상 `likeTargetId` 다. 상세에서 좋아요를 바꾸면 그 값은 상세 인스턴스 안에만 있고 목록은 모른다.

## 구조 (판단)

- 스토어 모듈.
  `src/community/feed-store.ts` 에 React 를 모르는 모듈 수준 스토어를 둔다. 키는 지금 Feed 의 key 와 같은 `(authorId, tag)` 문자열이다.
  한 키의 스냅샷은 행, 좋아요 수, 커서, done, 태그 총 개수, scrollY 다. 에러 여부, 삭제 다이얼로그, 오버레이 인덱스는 넣지 않는다.
  API 는 작게 둔다. 읽기(get), 되쓰기(set), 페이지 이어 붙이기(appendPage), 좋아요 수 갱신(setCount), 행 제거(remove, 모든 키에서), 키 비우기(invalidate), 전부 비우기(clear).
  페이지 이어 붙이기와 좋아요 수 갱신을 처음부터 두는 이유는 다음 기능 `lick-page` 의 플레이어가 같은 키의 목록을 읽어 다음 페이지를 받아 붙이고, 좋아요를 바꾸면 되돌아온 목록에 반영해야 하기 때문이다.
  `src/community/` 바로 아래에 두는 것은 `tags.ts`, `popular-tags.ts` 처럼 React 없는 모듈이 이미 그 자리에 있어서다. 단위 테스트는 그 모듈만으로 쓴다.
- 라이브 구독은 두지 않는다.
  라우트 모델에서 Feed 와 상세(다음 기능에서는 플레이어)는 Root 의 switch 때문에 동시에 마운트되지 않는다. 한쪽이 언마운트된 뒤 다른 쪽이 스토어를 읽으면 충분하다.
  목록과 플레이어가 한 화면에 함께 보이는 기능이 생기면 그때 useSyncExternalStore 를 더한다. 지금 넣으면 쓰는 곳 없는 경로가 된다.
- FeedList 의 흐름.
  마운트 때 스토어에 스냅샷이 있고 복원 조건이면 그것으로 상태를 초기화하고 첫 페이지 요청을 건너뛴다. 없거나 새로 받는 조건이면 지금과 같다.
  떠날 때 행, 좋아요 수, 커서, done, 태그 총 개수와 그 순간의 scrollY 를 되쓴다.
  scrollY 는 떠나는 순간의 값이어야 한다. 언마운트 정리 시점에 문서 높이가 이미 바뀌었을 수 있으므로, 레이아웃 정리 단계에서 읽거나 스크롤 때마다 적어 두는 쪽을 구현자가 고른다.
- 복원 정책.
  브라우저 뒤로 가기와 앞으로 가기(진짜 popstate)로 목록에 닿으면 복원한다. 코드 이동(navigate)으로 닿으면 처음부터 새로 받는다.
  버린 대안은 "일정 시간 안이면 항상 복원" 이다. 게시 뒤 Latest 탭을 눌렀을 때 내 새 릭이 안 보이고, 상세에서 지운 릭이 `/me` 에 남아 보이는 문제를 시간 상한으로는 못 막는다. 브라우저의 뒤로 가기 복원 관행과도 맞지 않는다.
  Latest 탭을 다시 눌러 새로 고치는 동작은 지금처럼 두고 범위 밖으로 둔다(지금은 아무 일도 없다).
  진짜 popstate 와 navigate 를 구분하는 표식의 자리는 사실 절의 셋 중에서 구현자가 고른다. 행동은 위와 같이 확정한다.
- 스토어를 비우거나 고치는 사건.
  게시 성공은 스토어 전체를 비운다. 게시 뒤 뒤로 가기로 Latest 에 닿아도 새 릭이 보여야 하고, 게시는 드물어 비용이 없다.
  삭제 성공은 모든 키에서 그 행을 뺀다. 내 릭에서 지운 뒤 Latest 복원본에 그 릭이 남지 않게 한다. 목록은 유지되므로 스크롤도 남는다.
  상세의 좋아요 토글(낙관적 반영과 실패 되돌림)은 setCount 로 스토어에도 적는다. 돌아온 카드가 바뀐 수를 보인다. 상세가 쓰는 스토어 API 는 다음 기능의 플레이어가 그대로 쓴다.
  내 릭의 이름 바꾸기 성공은 그 키를 비운다. 지금의 리마운트가 캐시를 읽어 옛 이름을 보이는 일을 막는다.
- 스크롤 복원.
  복원 마운트에서는 첫 커밋에 행이 모두 있으므로 문서 높이가 충분하다. 첫 그리기 전에 scrollY 를 되돌려 맨 위가 잠깐 보이는 점프를 없앤다.
  브라우저 자체 복원(auto)이 겹쳐 두 번 움직이는 일이 보이면 `history.scrollRestoration` 을 manual 로 둔다. 새로고침 때는 캐시가 없어 맨 위가 맞으므로 manual 로 두어도 잃는 것이 없다.
- 센티널과 진행 중 요청.
  복원된 위치에서 센티널이 보이면 다음 페이지가 한 번 받아진다. 머물러 있었어도 같은 일이 일어나므로 허용한다. 단 중복 행이 생기면 안 된다.
  떠날 때 진행 중이던 페이지 요청은 커서와 행이 어긋나지 않게 처리한다. 도착한 페이지를 스토어에 이어 붙이든 버리든, 복원된 목록의 커서는 마지막 행의 created_at 과 같아야 한다.
- 에러 상태.
  에러는 캐시하지 않는다. 행이 있는 스냅샷은 에러와 무관하게 복원하고 센티널이 다음 페이지를 다시 시도한다. 행이 없는 스냅샷(첫 페이지 실패)은 캐시가 없는 것으로 보고 처음부터 받는다.

## 종료 시나리오

폰 폭(390px)에서 확인한다. S11 만 데스크톱 폭(1280px)에서 확인한다.
로그인이 필요한 S5(내 릭), S6, S7, S8, S10 은 휴대폰에서 확인한다. 나머지는 Playwright 로 scrollY 와 목록 요청 수를 찍는다.
"목록 요청" 은 `/rest/v1/licks` 의 목록 조회를 뜻한다. 상세의 단건 조회와 좋아요 수 조회는 세지 않는다.

S1. Latest 를 두 페이지(40장) 내려 카드 본문을 탭해 상세로 간 뒤 브라우저 뒤로 가기를 누르면, 같은 40장이 목록 요청 없이 보이고 scrollY 가 떠날 때와 같다(1px 이내).
    "Loading" 문구나 빈 목록이 먼저 보였다가 채워지지 않는다.
S2. S1 에 이어 앞으로 가기를 누르면 상세가 다시 열리고, 다시 뒤로 가기를 누르면 S1 과 같이 복원된다.
S3. 상세에서 탭 바 Latest(또는 사이드바 Latest, 로고)로 들어오면 첫 페이지부터 새로 받고 맨 위다.
S4. 태그 피드 `/tag/:name` 에서 S1 과 같이 하면 같은 카드와 scrollY 로 복원되고, 헤더의 "N licks" 총 개수도 요청 없이 그대로다.
S5. 유저 페이지와 내 릭에서 S1 과 같이 하면 같은 카드와 scrollY 로 복원된다. 유저 페이지는 프로필 요청 하나는 다시 나가지만 목록 요청은 없다.
S6. 상세에서 좋아요를 누르고 뒤로 가기로 목록에 오면 그 카드의 좋아요 수가 바뀐 값이다. 다시 눌러 취소하고 돌아오면 원래 값이다.
S7. 내 릭에서 카드로 상세에 가 삭제하면 `/me` 가 새로 받아지고 그 릭이 없다. 이어서 뒤로 가기를 두 번 눌러(지워진 릭의 상세는 "Lick not found") 내 릭 복원본에 닿아도 그 릭이 없다.
S8. 릭을 게시한 뒤(`/lick/:new`) 탭 바 Latest 로 가면 새 릭이 맨 위다. 뒤로 가기를 거듭해 Latest 항목에 닿아도 새 릭이 보인다.
S9. 새로고침하면 처음부터 받고 맨 위다.
S10. 내 릭에서 이름을 바꾸면 목록을 다시 받아 카드의 작성자 이름이 새 이름이다(지금 동작 유지).
S11. 데스크톱 1280px 에서 S1 과 같다.
S12. 목록 맨 아래(센티널이 보이는 위치)에서 상세에 갔다 돌아오면 다음 페이지가 한 번 받아지고 중복 카드가 없다. 마지막 페이지였다면 "No more" 가 그대로다.

## 범위

포함:
- 키별 목록 스토어 모듈과 단위 테스트
- FeedList 의 복원과 되쓰기, 스크롤 복원
- 진짜 popstate 와 navigate 의 구분
- 게시, 삭제, 좋아요, 이름 바꾸기가 스토어에 미치는 반영
- 네 목록(Latest, 태그 피드, 유저 페이지, 내 릭) 모두

제외 (다음 기능 또는 다음 버전):
- `/lick/:id` 를 넘기기 플레이어로 바꾸는 일(`lick-page`). 플레이어가 스토어를 읽고 appendPage 와 setCount 를 쓰는 것은 그 기능에서 한다.
- 새 글 알림, 당겨서 새로 고침, Latest 탭 재탭으로 맨 위 가기나 새로 고침
- 검색 결과(`/search`)와 랭킹(`/ranking`) 목록의 캐시. 컴포넌트가 다르고 랭킹은 offset 페이지네이션이다.
- 유저 페이지 프로필과 내 릭 표시 이름의 캐시
- 탭이나 창 사이의 동기화. 스토어는 탭마다 따로다.
