# lick-page: 릭 상세와 넘기기 플레이어를 /lick/:id 한 화면으로 통합 기획

작성일: 2026-11-13. 모델: fable. 상태: 승인됨 (2026-11-13).

## 목적

릭을 보는 화면을 `/lick/:id` 하나로 만든다.
목록 카드에서 들어오면 그 목록 순서대로 위아래로 넘기며 듣고, 랭킹이나 검색이나 링크로 들어오면 한 장짜리로 열린다.
상세에만 있던 템포 조절, 음표 탭 재생, 작성자와 태그 링크, 유사 릭 안내, 작성자용 삭제, 배지를 이 화면이 모두 가지므로 오버레이 플레이어와 상세 페이지는 사라진다.

## 사용자 결정 (2026-11-11)

- `/lick/:id` 가 유일한 릭 화면이다. 그 안에서 위아래로 넘기고 오버레이는 없앤다.
- 악보 탭: 음표를 누르면 그 음부터 재생한다. 빈 곳을 누르면 멈춤과 재개다.
- 반복 토글은 없앤다. 4박 무음 간격의 자동 반복(player 의 `LoopGap`)이 대신한다.
- 템포 조절은 상단 바로 옮겨 그대로 남긴다. 연습 장면(클릭 예비박)은 다음 기능이다.
- 카드 본문 탭과 카드 재생 버튼은 둘 다 `/lick/:id` 로 가고 자동 재생 여부만 다르다.
- 출처 목록이 없는 진입(랭킹, Top Licks, 검색, 게시 직후, 딥링크)은 한 장짜리로 열리고 멈춘 상태로 시작한다.

## 사용자 결정 (2026-11-13, 열린 질문의 답)

- Q1 화면 셸: 폰은 앱 바와 탭 바 없는 전체 화면, 데스크톱은 3열 셸의 가운데 열이다.
- Q2 돌아온 목록의 스크롤: 넘기지 않았으면 떠날 때 위치, 넘겼으면 마지막으로 본 릭의 카드가 앱 바 바로 아래에 오게 맞춘다.

## 확정된 사실 (코드 조사)

라우팅과 history
- `routing.ts` 의 `navigate(path)` 는 `history.pushState(null, '', path)` 뒤 `pending = 'navigate'` 로 두고 합성 popstate 를 보낸다. state 를 받는 인자가 없다.
- `useRoute` 는 popstate 때만 URL 을 다시 읽는다. popstate 없이 `replaceState` 로 URL 만 바꾸면 Root 의 `route.id` 는 진입 때 값으로 남는다.
- `Root.tsx` 는 `route.name` 으로 switch 해 `<main class="c-main">` 에 뷰 하나를 둔다. `LickDetail` 은 `key={id}` 로 id 마다 새 인스턴스다.
- 모바일 앱 바와 탭 바, 데스크톱 앱 바와 사이드바와 Top Licks 는 모든 커뮤니티 라우트에서 DOM 에 있고 CSS 미디어쿼리로 보이고 숨는다. `.community` 는 탭 바 높이만큼 `padding-bottom: 72px + safe-area` 를 둔다. 라우트에 따라 셸을 빼는 분기는 지금 없다.
- `lastCommunityPath` 는 편집, 레거시 열람, 게시, 공유 리다이렉트를 뺀 마지막 경로다. `/lick/:id` 도 기록된다. 편집기 Exit 는 `navigate(lastCommunityPath)` 이고 경로만 있다.
- `lastNavKind()` 는 뒤로 가기, 앞으로 가기, 첫 로드에 `'history'`, `navigate()` 호출에 `'navigate'` 다(feed-cache R3). `history.scrollRestoration` 은 manual 이다(R4).
- 브라우저 사실. `history.state` 는 항목마다 따로 저장되고 뒤로 가기와 앞으로 가기에 그 항목의 값이 돌아온다. 새로고침에도 같은 항목이라 남는다. URL 에 없으므로 링크를 복사해 보내면 전달되지 않는다. `replaceState` 는 같은 항목의 URL 과 state 를 함께 바꾼다.
- 브라우저 사실. 모듈 변수는 문서가 살아 있는 동안만 남고 항목마다 따로가 아니다. 쿼리 문자열은 항목, 새로고침, 공유 링크 모두에 남지만 URL 이 길어지고 `/lick/:id` 가 유일한 주소가 아니게 된다.
- 브라우저 사실. 같은 문서 안의 탭, 클릭, 터치 이동, 휠, 키 입력 뒤에는 소리를 낼 수 있다. 뒤로 가기, 앞으로 가기, 새로고침, 주소 입력으로 도착한 문서에는 제스처가 없어 AudioContext 가 suspended 로 남는다. `main.tsx` 가 전역 pointerdown 에서 resume 한다.
- `history.length` 로는 직전 항목이 이 앱 안인지 알 수 없다. 딥링크로 연 문서의 `history.back()` 은 사이트 밖으로 나간다.

저장소와 마운트 순서
- `feed-store.ts` 는 `get`, `set`, `appendPage`, `setCount`, `remove`, `invalidate`, `clear` 를 가진다. `appendPage` 는 지금 부르는 곳이 없다. 스냅샷은 `rows`, `counts`, `cursor`, `done`, `total`, `scrollY` 다.
- FeedList 는 `useLayoutEffect` 의 정리 함수에서 스냅샷을 쓴다(feed-cache R6, R8). React 의 커밋 순서는 새 트리 렌더(useState 초기값 계산), 지워지는 트리의 레이아웃 정리, 새 트리의 레이아웃 이펙트, 패시브 이펙트다. 그래서 `/` 에서 `/lick/:id` 로 갈 때 새 화면의 useState 초기값은 떠나는 FeedList 가 아직 쓰지 않은 저장소를 읽고, useLayoutEffect 와 useEffect 는 쓴 뒤의 값을 읽는다. 반대로 `/lick/:id` 에서 목록으로 돌아갈 때 FeedList 의 useState 초기값은 떠나는 화면의 정리 함수보다 먼저 돈다.
- 복원 마운트 조건은 `lastNavKind() === 'history'` 이고 그 키의 스냅샷에 행이 있을 때다(R5). 복원은 첫 렌더에 행을 다 그리고 레이아웃 이펙트에서 `scrollTo(0, scrollY)` 를 두 번 부른다(R7).
- `LickRow` 에 `blob`, `tags`, `canonical_id`, `created_at`, `profiles(public_id, display_name)` 가 다 있다. 목록에서 온 화면은 단건 조회가 필요 없고 좋아요 수도 `counts` 에 있다. 내 좋아요 집합(`fetchMyLikedSet`)만 받으면 된다. 상세는 `fetchLick`, `fetchLikeCounts`, `fetchMyLikedSet` 셋을 받는다.
- FeedList 는 `playAt` 으로 오버레이를 띄우고, 출처 라벨을 `tag ? '#' + tag : authorId ? 첫 행 display_name ?? 'Licks' : 'Latest'` 로 계산하고, `onCount` 로 `counts` 를 갱신한다. `player` 와 `user` prop 은 오버레이에만 쓴다. 검색 결과의 LickCard 는 `onPlay` 가 없다.

## 구조 (판단)

### 1. URL 과 history

- 넘기면 URL 이 현재 장의 `/lick/:id` 로 따라 바뀐다. `history.replaceState` 다. popstate 를 내지 않으므로 Root 는 다시 렌더하지 않고 화면이 자체 상태로 현재 장을 안다.
- 뒤로 가기 한 번이 목록으로 돌아간다. 목록은 `lastNavKind() === 'history'` 라 feed-cache 복원이다.
- 앞으로 가기는 마지막으로 본 릭이다. 항목의 URL 이 그 릭으로 바뀌어 있기 때문이다.
- 버린 대안. 장마다 `pushState`. 뒤로 가기가 본 릭을 하나씩 거슬러 목록까지 열 번 넘게 눌러야 하고, 이전 릭은 아래로 넘기기가 이미 맡는다.
- 버린 대안. URL 을 진입 때 id 로 고정. 새로고침과 공유가 지금 보는 릭이 아니라 처음 릭을 열어 주소 표시줄을 믿을 수 없다.
- 돌아온 목록의 스크롤. 넘기지 않고 돌아오면 떠날 때의 scrollY 다(feed-cache 그대로). 다른 장으로 넘긴 뒤 돌아오면 마지막으로 본 릭의 카드가 앱 바 바로 아래에 오게 맞춘다. 열 장을 듣고 돌아왔을 때 이미 들은 카드 열 장을 다시 내려가지 않게 하기 위해서다. 사용자 취향이 갈릴 수 있어 열린 질문 Q2 로도 남긴다.
- 그 방법은 화면이 장을 바꿀 때마다 출처 스냅샷에 마지막 릭 id 를 적고, FeedList 의 복원 마운트가 그 id 의 카드가 있으면 scrollY 대신 그 카드로 스크롤하는 것이다. 사실 절의 커밋 순서 때문에 떠날 때 정리 함수에서 한 번 적는 방식은 FeedList 의 useState 초기값에 보이지 않는다. 장을 바꿀 때마다 적거나 FeedList 가 레이아웃 이펙트에서 읽어야 한다. 어느 쪽인지는 명세가 정한다.

### 2. 출처 목록 전달

- `navigate(path, state?)` 로 넓혀 `history.state` 에 `{ from: feedKey | null, autoplay: boolean, depth: number }` 를 넣는다. 카드 본문과 재생 버튼이 `from` 에 자기 목록의 `feedKey(authorId, tag)` 를 넣는다. 그 밖의 진입은 state 가 없거나 `from` 이 null 이다.
- 몇 번째 장인지는 state 에 두지 않는다. URL 의 id 를 스냅샷 `rows` 에서 찾아 그 인덱스로 연다. 넘기며 URL 을 바꾸므로 id 가 항상 현재 장이고 인덱스는 파생값이다.
- 화면은 마운트 때 레이아웃 이펙트에서 `history.state.from` 의 스냅샷을 읽고 행을 자기 상태로 복사한다. 렌더 중(useState 초기값)에 읽으면 사실 절의 순서 때문에 떠나는 FeedList 가 아직 쓰지 않은 값을 읽는다. 레이아웃 이펙트의 setState 는 첫 그리기 전에 반영되므로 빈 화면이 보이지 않는다.
- 스냅샷이 없거나, 행이 비었거나, URL 의 id 가 행에 없으면 한 장 모드다. 한 장 모드는 상세처럼 `fetchLick(id)` 와 `fetchLikeCounts` 를 받는다. 새로고침(저장소가 빈다), 딥링크, 출처 키의 스냅샷이 다른 목록 방문으로 덮인 경우가 여기 든다.
- 각 전달 방법이 어떻게 동작하는지는 사실 절에 적었다. history.state 를 고른 이유는 뒤로 가기와 앞으로 가기에 항목마다 제 값이 돌아오고, 새로고침에는 저장소가 비어 어차피 한 장 모드이며, 공유 링크에는 실려 가지 않아 `/lick/:id` 가 깨끗하게 남기 때문이다. 모듈 변수는 Latest 에서 연 릭과 태그 피드에서 연 릭을 오가면 마지막 값 하나만 남아 틀린다. 쿼리 문자열은 공유되는 주소를 더럽힌다.
- `depth` 는 이 문서 안에서 `navigate` 가 쌓은 깊이다. 첫 항목(딥링크, 새로고침)은 state 가 없어 0 이다. 닫기 버튼과 Esc 는 `depth > 0` 이면 `history.back()`, 아니면 `navigate('/')` 다. 딥링크로 연 화면의 닫기가 사이트 밖으로 나가지 않게 한다. 넘기기의 `replaceState` 는 `depth` 와 `from` 을 그대로 옮긴다.
- 화면 컴포넌트의 key 는 id 가 아니라 항목이다. 넘기며 id 가 바뀌어도 리마운트하지 않아야 하고, 진입 id 와 같은 릭으로 `navigate` 되는 경우(유사 릭에서 원본으로, 원본이 진입 id 인 경우)에는 리마운트해야 하기 때문이다. routing 이 popstate 마다 올리는 일련번호를 key 로 쓰는 것을 추천한다. 명세가 정한다.

### 3. 다음 페이지, 좋아요, 삭제의 저장소 반영

- 뒤에서 두 번째 장에 이르면 `fetchFeedPage(cursor, filter)` 와 `fetchLikeCounts` 로 다음 페이지를 받아(FeedList 의 loadMore 와 같은 순서) 자기 상태에 잇고 `feedStore.appendPage(from, rows, counts, done)` 을 부른다. 커서는 스냅샷의 `cursor` 에서 시작한다. 목록 모드의 `hasMore` 는 스냅샷의 `done` 이 false 일 때다.
- 돌아온 FeedList 는 복원 마운트에서 스냅샷 행을 모두 그리므로 화면이 받은 페이지가 그대로 보이고 센티널은 이어진 커서부터 받는다. 중복 행은 생기지 않는다. 진행 중이던 요청은 언마운트 뒤 버린다(FeedList 와 같은 `alive` 플래그).
- 좋아요는 목록 모드에서 스냅샷 `counts` 로 시작하고, 토글은 자기 상태와 `feedStore.setCount(likeTargetId, count)` 에 함께 쓴다(feed-cache R11 과 같다). 한 장 모드도 `setCount` 를 부른다. 스냅샷이 없으면 아무 일도 없다.
- 삭제 성공은 `feedStore.remove(id)` 다(R10).
- 출처 라벨은 키에서 유도한다. `'|'` 는 "Latest", `'|jazz'` 는 "#jazz", `'<uuid>|'` 는 첫 행의 `profiles.display_name`, 없으면 "Licks" (swipe-play R14 와 같다).

### 4. 자동 재생 규칙

- 자동 재생은 `lastNavKind() === 'navigate'` 이고 `history.state.autoplay === true` 일 때만이다. 카드 재생 버튼이 여기 든다. 같은 문서 안의 탭 뒤 이동이라 소리가 난다.
- 카드 본문 탭은 `autoplay: false` 라 멈춘 상태로 연다. INTAKE 의 "자동 재생 여부만 다르다" 그대로다. 본문을 누른 사람은 악보를 읽거나 태그와 작성자를 보거나 지우려는 것일 수 있어 소리를 내지 않는다. 두 진입이 모두 자동 재생이면 재생 버튼이 필요 없어지는데 재생 버튼은 2026-11-10 결정이다.
- 한 장 진입은 멈춤이다. 랭킹과 검색은 같은 문서 안의 탭이라 소리를 낼 수는 있지만 INTAKE 가 멈춤으로 정했고, 딥링크와 새로고침은 제스처가 없어 어차피 못 낸다. 규칙을 하나로 둔다.
- 뒤로 가기와 앞으로 가기로 이 화면에 닿으면 멈춤이다. `lastNavKind()` 가 `'history'` 라 자동 재생 조건에 들지 않는다. 제스처가 없어 소리를 못 내기도 한다.
- 멈춘 상태로 열린 장은 플레이헤드가 없고 멈춤 표시(반투명 원과 재생 삼각형)가 보인다. 빈 곳을 탭하면 0 부터 재생한다.
- 넘긴 뒤의 재생은 swipe-play R6 그대로다. 재생 중이었으면 새 장을 0 부터, 멈춘 상태였으면 멈춘 채 보인다.

### 5. 상단 바

- 페이저 밖에 한 줄이다. 왼쪽부터 닫기(34px 원형), 카운터 "3 / 40", 출처 라벨, 빈 공간, 템포 버튼 "100 bpm", 오버플로 메뉴 버튼(More actions, 작성자만).
- 폰 폭 390 에서 고정 폭 합은 좌우 패딩 24, 닫기 34, 카운터 약 52, 템포 약 65, 오버플로 44, 간격 40 으로 약 260px 이고 출처 라벨에 약 130px 이 남는다. 출처 라벨은 `min-width: 0` 과 말줄임이다(표시 이름은 30자 이하). 들어간다.
- 한 장 모드는 카운터와 출처 라벨을 숨긴다. "1 / 1" 과 출처 없음은 정보가 아니다. 닫기, 템포, 오버플로만 남는다.
- 템포 팝오버는 상단 바에서는 오른쪽 정렬로 연다. 사실 절의 `left: 0` 기준 280px 이 폰에서 넘치기 때문이다. 디자인 단계에서 그린다.
- 상단 바 높이는 템포 버튼의 44px 때문에 지금 오버레이의 50px 보다 조금 커진다. 디자인이 정한다.

### 6. 장 하나의 구성

- 장은 세로 스냅 페이저의 한 칸이고 높이가 페이저와 같다(R6). 안은 본문(세로 스크롤, R15)과 장 하단 고정 액션 행이다.
- 본문은 위에서 아래로: 제목 줄(제목 17px 600, "Key of C" 배지, "N bars" 배지, 줄바꿈 허용), 작성자 링크와 날짜(11px mut2), 유사 릭 안내 한 줄(canonical_id 가 있을 때, 원본 링크 포함), 악보 프레임(1px ink, radius 12, 툴바 없음), 태그 칩 링크, 끝 캡션 또는 불러오기 실패와 Retry(R9), 긴 릭 캡션(R15).
- 제목을 악보 위에 두는 것은 상세의 순서다. 오버레이는 악보를 먼저 두었는데 8마디 릭에서 제목과 작성자가 접히는 영역 아래로 내려가 보이지 않았다. 제목 줄과 메타는 합쳐 약 70px 이라 4마디 릭의 악보가 폰에서 접히지 않는다.
- 악보 프레임 안에는 플레이헤드, 멈춤 표시, 카운트다운(R8)이 지금처럼 겹친다.
- 액션 행은 Duplicate & edit, 좋아요 수, Share 순서로 장 하단에 고정한다(R11, R16). 긴 릭의 본문 스크롤과 무관하게 닿는다.
- 처음 한 번 힌트(R10)와 토스트는 페이저 위에 겹친다. 한 장 모드에는 힌트가 없다.
- 작성자와 태그는 링크다. swipe-play R12 의 "표시만" 을 뒤집는다. 이 화면이 상세이기도 하므로 상세의 링크를 잃을 수 없다.

### 7. 악보 탭

- 음표를 누르면 그 음의 시작 스텝부터 끝까지 재생한다. 멈춘 상태였으면 재생 상태가 되고, 재생 중이었으면 그 음부터 다시 시작한다. 카운트다운 중이면 간격을 버리고 그 음부터다. 반복 옵션은 늘 `{ gapBeats: 4 }` 다.
- 빈 곳을 누르면 멈춤과 재개다(R7). 재개는 마지막 진행 스텝부터, 카운트다운 중에 멈췄으면 0 부터다.
- 같은 클릭을 두 번 처리하지 않는다. 사실 절대로 음표 `<g>` 의 onClick 은 전파를 막지 않으므로, 프레임 핸들러는 클릭 대상이 `[data-note]` 안이면 아무것도 하지 않거나 음표 핸들러가 전파를 멈춘다. Score 를 고치지 않고 화면 쪽에서 가린다. 명세가 하나를 고른다.

### 8. 템포

- 장마다 그 곡의 템포로 시작한다. 바꾼 값은 그 장에 머무는 동안만 유효하고 다른 장으로 넘기면 버린다. 릭마다 원 템포가 60 ~ 240 으로 달라 절대값을 옮기면 다음 릭이 엉뚱한 속도가 된다. 비율 유지는 연습 장면이라 범위 밖이다.
- 재생 중 바꾸면 현재 위치부터 새 템포로 이어 재생한다(상세와 같다). 간격 중이면 0 부터 새 템포다. 멈춘 상태에서는 값만 바뀌고 다음 재생부터 적용된다.
- 4박 간격도 세션 템포를 따른다. 플레이어에 넘기는 곡이 `{ ...song, tempo }` 이기 때문이다.
- 장이 바뀌면 열려 있던 팝오버를 닫는다.

### 9. 삭제 흐름

- 오버플로 메뉴와 확인 다이얼로그는 상세의 `OverflowMenu`, `DeleteLickDialog` 그대로다. 작성자가 아니면 오버플로 버튼을 그리지 않는다.
- 성공하면 `feedStore.remove(id)` 와 토스트 "Lick deleted" 다.
- 목록 모드에서 다른 장이 남으면 그 장을 빼고 이웃으로 간다. 다음 장, 없으면 이전 장이다. URL 을 `replaceState` 로 그 릭으로 바꾸고 재생은 R6 규칙(재생 중이었으면 0 부터, 멈춘 상태면 멈춤)이다. 뒤로 가기로 닿는 목록 복원본에는 그 릭이 없다.
- 남는 장이 없거나 한 장 모드면 상세와 같이 `navigate('/me')` 다.
- 실패는 다이얼로그 안에 "Delete failed. Please try again." 이다(상세와 같다).

### 10. 나가기와 돌아오기

- 닫기 버튼과 Esc: 구조 2 의 `depth` 규칙이다. 소리는 언마운트에서 멈춘다.
- 복제 편집: `navigate('/edit#' + blob)` 다. 상세와 같다. 오버레이의 `replaceState` 꼼수(R11)는 오버레이가 페이지가 아니어서 필요했고 이제 `/lick/:id` 는 페이지다.
- 편집기 Exit: `lastCommunityPath` 에 경로와 함께 그때의 `history.state` 도 남기고 `navigate(path, state)` 로 돌아온다. 출처 스냅샷이 남아 있으면 목록 모드가 그대로 돌아온다. 소리는 멈춘 상태다(`autoplay` 는 `navigate` 가 세우는 값이 아니라 state 의 값이므로 false 로 바꿔 넘긴다). 게시를 거쳐 저장소가 비면 한 장 모드다.
- 작성자 링크와 태그 칩: `navigate('/user/:public_id')`, `navigate('/tag/:name')` 이다. 새 마운트라 첫 페이지부터 받는다. 뒤로 가기로 돌아오면 state 가 그대로라 같은 장이 멈춘 채 열린다.
- 유사 릭 원본 링크: `navigate('/lick/:canonical')` 이고 state 가 없어 한 장 모드다. 뒤로 가기로 출발한 장에 돌아온다.
- 공유: `/s/:id` 그대로(R11). `navigator.share` 가 있으면 공유 시트, 아니면 클립보드와 "Link copied".

### 11. 데스크톱과 키보드

- 키보드는 R13 과 같다. ArrowDown 과 ArrowUp 은 한 장 이동, Space 는 멈춤과 재개, Esc 는 닫기. 마운트 때 닫기 버튼에 포커스를 둔다.
- 포커스가 템포 팝오버나 오버플로 메뉴나 다이얼로그 안에 있으면 페이지 키를 받지 않는다. range input 의 화살표가 장을 넘기면 안 된다.
- 레이아웃은 열린 질문 Q1 이다. 추천은 폰에서 앱 바와 탭 바 없는 전체 화면, 데스크톱에서 3열 셸의 가운데 열이다. 스크림 위 패널(지금 오버레이)은 뒤에 목록이 있을 때의 모양이라 라우트가 바뀌어 뒤가 빈 지금은 의미가 없다.

- 상세의 테스트는 전부 새 화면으로 간다: 공유 URL, 유사 릭 안내와 원본 링크, 태그 칩, 복제 편집, 좋아요 single-flight 와 비로그인 토스트, 오버플로와 삭제 다이얼로그, 로드 실패와 Retry, feed-cache AC-16 과 AC-17.

### 13. swipe-play 와 상세에서 바뀌는 규칙

- R4 열기와 닫기: history 항목은 `navigate` 가 만들고 닫기는 `depth` 규칙이다. popstate 구독이 없다.
- R5 즉시 재생: 자동 재생 조건이 붙는다(구조 4).
- R7 멈춤과 재개: 음표 탭은 그 음부터 재생이다(구조 7). SPEC 4절과 일치하게 된다.
- R11 복제 편집: `navigate` 다. 좋아요는 `setCount` 다.
- R12 표시만: 링크다.
- R13 데스크톱: 스크림 패널이 아니다(Q1).
- R16 장의 구성: 제목이 악보 위로 가고 배지, 메타 링크, 유사 릭 안내가 더해진다. 상단 바에 템포와 오버플로가 더해진다.
- 상세의 Loop 토글과 즉시 되감기: 없어지고 4박 간격 자동 반복이다. 상세의 Play 버튼: 없어지고 빈 곳 탭이다.
- 상세의 `key={id}` 리마운트: 항목 단위 key 로 바뀐다(구조 2).

## 종료 시나리오

폰 폭(390x844)에서 확인한다. (데스크톱) 표시는 1280x800 이다.
(폰, 로그인) 표시는 Playwright 로 로그인할 수 없어 휴대폰에서 확인하고 `verdict.md` 의 휴대폰 확인 표에 적는다.
"목록 요청" 은 feed-cache 명세와 같이 `/rest/v1/licks` 중 `id=eq.` 가 없는 것이다.
셸(앱 바와 탭 바의 유무)은 Q1 의 답을 따른다.

S1. Latest 에서 세 번째 카드의 재생 버튼을 누르면 URL 이 `/lick/:id` 가 되고 그 릭이 바로 재생된다(1초 안에 플레이헤드).
    상단 바에 닫기, "3 / 20", "Latest", "100 bpm" 이 보이고, 장에 제목, Key of C 와 N bars 배지, 작성자 링크와 날짜, 악보, 태그 칩, 하단 고정 액션 행(Duplicate & edit, 좋아요 수, Share)이 보인다.
S2. Latest 에서 카드 본문을 누르면 같은 화면이 열리지만 멈춘 상태다. 플레이헤드가 없고 멈춤 표시가 보인다. 악보의 빈 곳을 탭하면 0 부터 재생된다.
S3. S1 에서 위로 넘기면 다음 릭이 즉시 처음부터 재생되고, URL 이 그 릭의 `/lick/:id` 로 바뀌며, `history.length` 는 그대로다. 카운터가 "4 / 20" 이다. 아래로 넘기면 앞 릭으로 돌아가 처음부터 재생된다.
S4. 한 릭이 끝나면 소리 없이 4 3 2 1 이 박 간격으로 보이고 4박 뒤 처음부터 다시 재생된다. 카운트다운 중 넘기면 다음 릭이 바로 난다.
S5. 멈춘 상태에서 악보의 음표를 탭하면 그 음부터 재생된다(플레이헤드가 그 음표의 x 에서 시작). 재생 중에 다른 음표를 탭하면 그 음부터 다시 시작한다. 음표 탭으로 멈추지 않는다.
S6. 재생 중 빈 곳을 탭하면 멈추고(플레이헤드가 남는다) 다시 탭하면 그 자리부터 이어진다. 카운트다운 중 탭하면 멈추고 다시 탭하면 0 부터다.
S7. "100 bpm" 을 누르면 팝오버가 열리고 + 를 누르면 "105 bpm" 이 되며 재생은 현재 위치에서 새 템포로 이어진다. 다음 릭으로 넘기면 그 릭의 원 템포가 보인다.
S8. S3 처럼 두 장 넘긴 뒤 브라우저 뒤로 가기를 누르면 소리가 멈추고 Latest 가 목록 요청 없이 복원되며 마지막으로 본 릭의 카드가 앱 바 바로 아래에 있다(Q2). 넘기지 않고 돌아오면 떠날 때의 scrollY 다(1px 이내).
S9. S8 에 이어 앞으로 가기를 누르면 마지막으로 본 릭이 멈춘 채 열리고 카운터와 출처가 그대로다.
S10. `/lick/:id` 에서 새로고침하면 그 릭이 한 장으로 멈춘 채 열린다. 카운터와 출처 라벨이 없고 위아래로 넘겨지지 않는다. 닫기를 누르면 `/` 로 간다.
S11. 랭킹 행과 검색 제안으로 들어가면 S10 과 같은 한 장 화면이 멈춘 채 열린다. (데스크톱) Top Licks 도 같다.
S12. 작성자 이름을 누르면 `/user/:public_id` 로 가고 뒤로 가기로 돌아오면 같은 릭이 같은 카운터로 멈춘 채 열린다. 태그 칩을 누르면 `/tag/:name` 으로 가고 돌아올 때도 같다.

S17. 8마디 릭(피드 응답의 blob 치환)을 열면 악보가 장 안에서 세로로 스크롤되고 "Scroll for the rest of the score" 가 보이며 액션 행은 화면 하단에 남는다. 끝까지 내린 뒤 한 번 더 밀면 다음 장이다.

## 엣지케이스

- 출처 스냅샷에 URL 의 id 가 없다(새로고침, 스냅샷이 덮임, 지워짐). 한 장 모드다.
- 출처와 같은 키의 목록을 링크로 다녀오면 스냅샷이 새 첫 페이지로 덮인다(예: `/tag/jazz` 에서 연 장에서 #jazz 칩을 누르고 돌아옴). 돌아온 장의 id 가 새 스냅샷에 있으면 그 인덱스로, 없으면 한 장 모드다.
- `history.state` 가 없는 항목(주소 입력, 외부 링크)은 한 장 모드이고 `depth` 0 이라 닫기가 `/` 로 간다.
- 템포 팝오버가 열린 채 넘기면 닫는다. 팝오버 안의 range 와 버튼은 페이지 키를 받지 않는다.
- 간격 중 템포를 바꾸면 0 부터 새 템포다.
- 목록 모드에서 마지막 남은 장을 지우면 `/me` 다. 한 장 모드의 삭제도 `/me` 다.
- 로그인하지 않았으면 오버플로 버튼이 없다. 열려 있는 동안 로그인 상태가 바뀌면 다음 렌더부터 반영한다(E8).
- `fetchMyLikedSet` 은 마운트 때 한 번이다. 장마다 받지 않는다.
- 한 장 모드의 `fetchLick` 실패는 "Couldn't load this lick." 과 Retry 다(상세와 같다).
- 음표 탭 한 번에 토글이 같이 돌지 않는다(구조 7).
- 넘기기 중 들어오는 `appendPage` 는 현재 장을 다시 시작하지 않는다(ref 로 읽는다, 오버레이와 같다).
- 떠날 때 진행 중이던 다음 페이지 요청은 버린다. 스냅샷 커서는 반영된 마지막 행이다.
- 폰에서 페이저의 `overscroll-behavior: contain` 으로 당겨서 새로 고침이 끼어들지 않는다. iOS 의 가장자리 가로 스와이프(뒤로 가기)는 세로 넘기기와 충돌하지 않는다.
- 화면 회전과 리사이즈는 장 높이와 악보 폭을 다시 잰다(E9).
- 템포 60 의 4박 간격은 4초, 240 은 1초다(E11).
- 편집기에서 Share 로 게시하면 저장소가 비므로 Exit 로 돌아와도 한 장 모드다.
- 유사 릭의 좋아요 수는 `likeTargetId` 로 원본 것이다. 한 장 모드와 목록 모드 모두 같다.

## 범위

포함:
- `/lick/:id` 새 화면(목록 모드와 한 장 모드), 상단 바(닫기, 카운터와 출처, 템포, 오버플로), 장 구성, 음표 탭과 빈 곳 탭, 4박 간격 자동 반복, 템포 조절, 자동 재생 규칙
- `navigate(path, state)` 와 `history.state`(`from`, `autoplay`, `depth`), 넘기기의 `replaceState`, 항목 단위 key, 닫기 규칙
- 저장소 읽기, `appendPage`, `setCount`, `remove`, 돌아온 목록의 마지막 릭 앵커(Q2)
- 작성자와 태그 링크, 유사 릭 안내, 작성자용 삭제와 이웃 이동, 좋아요, 공유, 복제 편집, 편집기 Exit 의 state 전달
- 카드 본문과 재생 버튼의 진입 전환, `PlayOverlay` 와 `LickDetail` 과 `ScoreFrame` 과 관련 CSS 와 테스트 제거, Feed 의 `playAt` 과 `player`, `user` prop 제거
- 데스크톱 레이아웃과 키보드(Q1)
- 처음 한 번 힌트, 긴 릭 장 안 스크롤
- 문서: SPEC 4.1 절을 라우트 모델로 고쳐 쓰고 4절의 열람 설명에 음표 탭 규칙이 이 화면에도 적용됨을 적는다. DECISIONS 에 이 기획의 판단(replaceState, history.state, 자동 재생 조건, 셸)을 남긴다

제외 (다음 기능 또는 다음 버전):
- 연습 장면: 클릭 예비박, 장 사이 템포 비율 유지, 메트로놈 토글, N회 반복 뒤 자동 다음
- `/s/:id` 의 목적지 변경(지금은 레거시 열람 `/?mode=view#blob`). 공유 링크를 이 화면으로 보내는 일은 별도 기능
- 검색 결과 카드의 재생 버튼과 출처 목록, 랭킹을 출처로 하는 넘기기. 두 목록은 feed-cache 가 캐시하지 않는다
- 게시 화면 `ScoreToolbar` 의 반복 토글 정리
- 사이드바의 Latest 첫 페이지 중복 요청
- Wake Lock, 백그라운드 재생
- 상세 전용 `/lick/:id?view=…` 같은 보기 모드

세션 분할 제안.
이 기능은 한 세션을 넘길 가능성이 크다(새 화면 하나, 라우팅 변경, 두 화면 제거, 단위 기준 약 30개, 시나리오 24개).
자르려면 다음 순서로 태스크를 두어 첫 묶음 뒤에 동작하는 상태로 멈춘다.
- 첫 묶음: 한 장 모드까지. 새 화면이 `LickDetail` 을 대체한다(상단 바 템포, 음표 탭과 빈 곳 탭, 자동 반복, 배지, 링크, 유사 릭 안내, 삭제). 오버레이와 카드 재생 버튼은 그대로 둔다. 여기까지로도 상세가 자동 반복과 새 레이아웃을 얻는다.
- 둘째 묶음: 목록 모드. `navigate` state, 저장소 읽기와 `appendPage`, 넘기기와 `replaceState`, 자동 재생, 삭제 시 이웃 이동, 카드 버튼 전환, 오버레이와 Feed `playAt` 제거, 돌아온 목록 앵커, 데스크톱과 키보드, 문서.
두 묶음을 기능 둘로 나누지는 않는다. 첫 묶음만 끝난 상태는 플레이어가 둘인 지금과 같고 그 자체가 목표가 아니기 때문이다.

- community (피드, 좋아요, 라우팅, 삭제)
- swipe-play (player 의 `LoopGap` 과 `onGap`, 카드 재생 버튼, 페이저와 현재 장 판정, 카운트다운, 긴 릭 스크롤, 힌트)
- feed-cache (스냅샷 저장소, `lastNavKind`, 복원 마운트, `scrollRestoration` manual)

## 열린 질문

둘 다 2026-11-13 에 사용자가 추천대로 답했다. 답은 "사용자 결정 (2026-11-13)" 절에 있고, 아래는 질문할 때의 근거로 남긴다.

Q1. 화면 셸. 폰에서 이 화면이 앱 바와 탭 바를 가진 커뮤니티 셸 안에 있는가, 쇼츠처럼 전체 화면인가. 데스크톱에서 3열 셸의 가운데 열 안인가, 지금 오버레이처럼 홀로 뜨는 680px 패널인가.
- 배경. 지금 상세는 셸 안(폰 729px 높이, 데스크톱 가운데 열 692px)이고 오버레이는 전체 화면(폰 844px, 데스크톱 스크림 위 680px 패널)이다. 둘을 합치면 하나를 골라야 한다. 라우트가 바뀌면 목록이 뒤에 없으므로 데스크톱의 스크림 패널은 그대로 두면 빈 셸 위에 패널이 뜨는 모양이 된다.
- 예시. 폰 셸 안이면 4마디 릭(악보 약 480px)에 제목 줄, 태그, 액션 행을 더하면 729px 을 거의 다 쓰고 8마디는 장 안 스크롤이 길어진다. 전체 화면이면 115px 이 더 남고 닫기 버튼이 유일한 나가는 길이 된다. 데스크톱 가운데 열이면 사이드바 태그와 Top Licks 가 옆에 남고, 홀로 뜨는 패널이면 상세가 앱에서 유일하게 셸 없는 화면이 된다.
- 파급. 셸 안이면 Root 의 셸 분기가 필요 없고 탭 바가 보인다(활성 탭은 없다). 전체 화면이면 Root 가 `/lick/:id` 에서 모바일 앱 바와 탭 바를 빼거나 CSS 로 가리고 `.community` 의 하단 패딩도 빼야 한다. 데스크톱 가운데 열이면 페이저 높이를 `100dvh - 앱 바 - 패딩` 으로 잡고 Esc 와 닫기는 뒤로 가기다.
- 추천. 폰은 전체 화면(앱 바와 탭 바 없음), 데스크톱은 3열 셸의 가운데 열. 폰은 세로 공간이 악보 가독성에 직결되고 넘기기가 탭 바와 같은 하단 영역에서 겹치지 않는 편이 낫다. 데스크톱은 공간이 남고 셸이 있어야 랭킹과 태그로 바로 갈 수 있으며 스크림 패널은 라우트 모델과 맞지 않는다. 시안은 디자인 단계에서 두 폭 모두 그린다.

Q2. 넘긴 뒤 뒤로 가기로 돌아온 목록의 스크롤. 떠날 때 위치(feed-cache 그대로)인가, 마지막으로 본 릭의 카드가 보이게 맞추는가.
- 배경. feed-cache 는 떠날 때의 scrollY 를 되살린다. 넘기기 뒤에는 "보던 카드" 가 떠난 카드가 아니라 마지막으로 들은 릭일 수 있다.
- 예시. Latest 셋째 카드에서 열어 열 장을 듣고 돌아왔을 때, 떠날 때 위치면 셋째 카드가 보이고 들은 열 장을 다시 지나 내려가야 한다. 앵커면 열세째 카드가 앱 바 아래에 보이고 그다음부터 이어 볼 수 있다.
- 파급. 떠날 때 위치는 만들 것이 없다(feed-cache S1 그대로). 앵커는 스냅샷에 마지막 릭 id 를 적는 필드와 FeedList 복원 마운트의 분기가 생기고, feed-cache 의 "scrollY 가 같다" 기준은 넘기지 않은 경우로 좁아진다.
- 추천. 앵커. 넘기지 않았으면 떠날 때 위치, 넘겼으면 마지막 릭 카드. 탐색 장면에서 들은 릭을 다시 지나지 않는 쪽이 이 기능의 목적(귀로 골라 보는 탐색)에 맞다.
