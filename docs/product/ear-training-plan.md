# 청음 훈련 기획

작성일: 2026-11-02.
상태: 초안.
근거: 현재 Lick Share 구현 (`/Users/randy/claude_code/lick_share/scorelink`, 배포본 https://lickshare.pages.dev 와 동일).

## 1. 목적

Lick Share 는 지금 릭을 만들고 공유하고 좋아요를 누르는 데서 끝난다.
이 기획은 공유된 릭을 모아 재생목록을 만들고, 그 재생목록으로 휴대폰에서 청음 테스트를 하는 흐름을 더한다.
듣기만 하던 릭을 귀로 받아 적는 훈련 재료로 바꾸는 것이 목표다.

사용자 흐름은 네 단계다.

1. 릭 생성
2. 릭 공유
3. 공유된 릭으로 재생목록 생성
4. 재생목록으로 청음 테스트 (휴대폰)

## 2. 현재 구현과 새로 만들 것

| 단계 | 현재 상태 | 새로 만들 것 |
|---|---|---|
| 1. 릭 생성 | 있음. 드럼 패드 입력, 피아노 실시간 녹음, 코드 반주, 데스크톱 피아노롤 (`src/ui/`) | 없음 |
| 2. 릭 공유 | 있음. URL 해시 공유 (`?mode=view#v2…`), 게시 후 `/lick/:id`, 단축 링크 `/s/:id` (`src/community/`) | 없음 |
| 3. 재생목록 | 없음 | DB 테이블, 담기 동작, 내 재생목록 화면, 재생목록 공유 링크, 연속 재생 |
| 4. 청음 테스트 | 없음 | 문제 진행 화면, 답 입력, 채점, 결과 화면, 휴대폰 오디오 보강 |

다시 쓸 수 있는 기존 부품은 다음과 같다.

- 곡 모델과 코덱
  - `src/core/types.ts` 의 `Song`, `Note`
  - `src/core/codec.ts` 의 `encodeSong`, `decodeSong`
  - 게시된 릭의 `blob` 이 이 형식이라 문제 데이터로 그대로 쓴다.
- 재생
  - `src/engine/schedule.ts`, `src/adapters/player.ts`
  - 반주와 메트로놈 켜고 끄기, 템포 변경이 이미 된다.
  - 문제 재생과 힌트 조절에 쓴다.
- 답 입력
  - 드럼 패드 (`src/ui/components/edit/Pad.tsx`)
  - 녹음 피아노 (`src/ui/components/edit/RecordingPiano.tsx`, `src/core/recording.ts`)
  - 편집 로직 (`src/core/editing.ts`)
  - 휴대폰 입력 UX(User Experience, 사용자 경험)가 이미 다듬어져 있다.
- 악보 표시
  - `src/ui/components/edit/Score.tsx`
  - 정답과 내 답을 겹쳐 보여 주는 데 쓴다.
- 멜로디 정규화
  - `src/community/melody-hash.ts` 의 `melodyTokens`
  - 첫 음 대비 피치 간격, 시작 오프셋, 길이로 정규화한다.
  - 조옮김과 무관한 채점에 그대로 쓸 수 있다.
- 계정과 권한
  - Supabase 인증, `profiles`, RLS(Row Level Security, 행 수준 보안) 패턴 (`supabase/schema.sql`)

## 3. 핵심 결정

결정마다 추천안을 적었다.
최종 확정은 10절 열린 질문에서 받는다.

### 3.1 청음 테스트 형식

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 받아쓰기 | 릭을 듣고 패드나 피아노로 똑같이 입력, 음 단위로 채점 | 진짜 청음 훈련. 기존 입력 부품을 그대로 씀 | 휴대폰 입력이 느림. 채점 규칙이 필요 |
| B. 고르기 | 릭을 듣고 보기 악보 3 ~ 4개 중 하나 선택 | 만들기 쉽고 빠름. 출퇴근길에 한 손으로 가능 | 악보를 눈으로 대조하는 퀴즈가 되기 쉬움 |
| C. 부분 받아쓰기 | 일부 음을 가리고 가린 음만 입력 | 난이도 조절이 쉬움 | 가릴 위치를 정하는 규칙이 추가로 필요 |

추천: A 받아쓰기를 첫 버전으로 한다.

- 이 앱의 강점이 휴대폰에서 다듬어진 패드 입력이라 A가 가장 잘 맞는다.
- B와 C는 같은 문제 진행 화면에 모드만 더하면 되므로 다음 버전으로 미룬다.

### 3.2 채점 기준

추천: 상대 음정으로 채점한다.

- 첫 음은 힌트로 제공한다. 첫 음 피치와 시작 위치를 미리 찍어 둔다.
  - 절대음감 테스트가 아니라 음정과 리듬 테스트가 되게 하려는 것이다.
- 비교 단위는 `melodyTokens` 와 같은 삼중항(피치 간격, 시작 오프셋, 길이)이다.
- 음마다 아래 셋 중 하나로 판정한다.
  - 정답: 시작 위치와 피치가 맞음
  - 리듬만 맞음: 시작 위치는 맞고 피치가 틀림
  - 놓침: 그 위치에 답한 음이 없음
- 정답 위치에 없는 음은 "추가된 음"으로 따로 센다.
- 점수는 `정답 음 수 / 정답 릭의 음 수` 다. 추가된 음은 점수에서 빼지 않고 결과 화면에만 표시한다.
- 길이(음가)는 첫 버전에서 채점하지 않는다.
  - 휴대폰 패드 입력에서 길이를 정확히 맞추기 어렵다.
  - 길이까지 보면 같은 멜로디를 듣고도 점수가 크게 떨어진다.
  - 10절 Q3에서 확인한다.

채점은 순수 함수로 `src/core/` 에 둔다.
DOM 이나 오디오에 의존하지 않으므로 기존 레이어 규칙과 맞는다.

### 3.3 문제 출제 방식

- 재생목록의 릭을 순서대로 또는 섞어서 낸다. 시작 화면에서 고른다.
- 조옮김은 첫 버전에서 하지 않는다. 릭을 원래 조 그대로 낸다.
  - 상대 음정 채점이라 조옮김을 해도 채점 로직은 같다.
  - 무작위 조옮김은 다음 버전에서 옵션으로 넣는다.
- 문제마다 할 수 있는 조작
  - 재생 (횟수 제한 없음, 재생 횟수는 기록)
  - 템포 낮추기 (원래 템포의 50 ~ 100%)
  - 반주 켜고 끄기 (코드 진행이 힌트가 됨)
  - 제출, 건너뛰기

### 3.4 재생목록 저장 위치

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. Supabase 테이블 | `playlists`, `playlist_items` 테이블, 링크 `/p/:id` | 길이 제한 없음. 기존 게시, 좋아요 구조와 같음. 나중에 기록 저장으로 넓히기 쉬움 | 만들려면 로그인 필요 |
| B. URL에 릭 id 나열 | `/p#<id,id,…>` | 서버 상태 없음. URL 공유 철학과 맞음 | 릭 id가 8자라 URL 500자 제한에서 50개 남짓이 한계. 이름, 순서 편집, 소유 개념이 없음 |

추천: A Supabase 테이블.

- 만드는 사람만 로그인하면 되고, 링크를 받은 사람은 로그인 없이 듣고 테스트할 수 있다.
- 기존 원칙대로 자체 서버 없이 `anon` key와 RLS로만 권한을 통제한다.

재생목록에 담을 수 있는 것은 게시된 릭(`licks.id` 가 있는 것)으로 한정한다.
게시하지 않은 URL 해시 릭은 먼저 게시하도록 안내한다.

### 3.5 테스트 기록

추천: 첫 버전은 세션 결과 화면까지만 하고 기록을 저장하지 않는다.

- 기록을 저장하려면 테이블, 개인정보 범위, 오답 재출제 규칙을 함께 정해야 해서 범위가 커진다.
- 결과 화면에서 "틀린 문제만 다시 풀기"는 메모리 상태로 제공한다.
- 기록 저장, 오답 노트, 간격 반복은 다음 버전으로 미룬다.

## 4. 데이터 모델 (초안)

`supabase/schema.sql` 에 추가한다.
최종 컬럼은 명세 단계에서 확정한다.

```sql
create table playlists (
  id text primary key default gen_short_id(8),
  owner_id uuid not null default auth.uid()
    references profiles(id) on delete cascade,
  title text not null,
  created_at timestamptz not null default now()
);

create table playlist_items (
  playlist_id text not null references playlists(id) on delete cascade,
  lick_id text not null references licks(id) on delete cascade,
  position int not null,
  primary key (playlist_id, lick_id)
);
```

- 읽기는 누구나, 쓰기는 소유자만 (`owner_id = auth.uid()`).
- 릭이 지워지면 재생목록에서도 빠진다 (`on delete cascade`). 10절 Q4에서 확인한다.
- 같은 릭은 한 재생목록에 한 번만 담는다.

## 6. 휴대폰 고려사항

테스트는 휴대폰에서 하는 것이 기본이다.

- 무음 모드
  - iPhone 은 무음 스위치가 켜져 있으면 Web Audio 소리가 나지 않을 수 있다.
  - 지금 코드는 `audioCtx.resume()` 만 하고 있다 (`src/main.tsx`).
  - Safari의 `navigator.audioSession.type = 'playback'` 적용을 검토한다.
  - 안 되면 첫 재생 때 안내 문구를 띄운다.
- 화면 꺼짐
  - 문제를 듣고 생각하는 동안 화면이 꺼지지 않게 Wake Lock API를 쓴다.
  - 지원하지 않는 브라우저에서는 조용히 넘어간다.
- 한 손 조작
  - 재생과 제출 버튼은 엄지가 닿는 하단에 둔다.
  - 답 입력 영역은 기존 모바일 편집 화면의 패드 배치를 그대로 쓴다.
- 이어폰
  - 블루투스 이어폰은 지연이 있다.
  - 받아쓰기는 재생과 입력이 분리돼 있어 문제가 없다.
  - 녹음 피아노로 답할 때는 지연이 거슬릴 수 있어 패드 입력을 기본으로 한다.

## 7. 기능 분해

whooing 하네스의 기능 단위 방식을 따른다.
기능 하나는 화면부터 DB까지 관통하는 시나리오 하나다.
full 은 화면이 있는 기능, light 는 화면 없이 테스트로 끝나는 기능이다.

| 순서 | id | 제목 | 트랙 | 의존 | 종료 시나리오 요지 |
|---|---|---|---|---|---|
| 1 | `playlist-schema` | 재생목록 테이블과 API | light | 없음 | 스키마 적용 후 API 테스트에서 소유자만 만들고 고치고 지울 수 있고, 다른 사용자와 비로그인 사용자는 읽기만 된다. |
| 2 | `playlist-build` | 재생목록 만들고 담기 | full | `playlist-schema` | `/lick/:id` 에서 "재생목록에 담기"로 새 재생목록을 만들면 `/playlists` 에 보이고, `/p/:id` 에 그 릭이 보인다. 순서를 바꾸고 빼면 새로고침해도 유지된다. |
| 3 | `playlist-play` | 재생목록 공유와 연속 재생 | full | `playlist-build` | 비로그인 휴대폰에서 `/p/:id` 를 열고 연속 재생을 누르면 릭이 순서대로 재생되고 지금 재생 중인 릭이 강조된다. |
| 4 | `quiz-grading` | 받아쓰기 채점 | light | 없음 | 정답과 답 노트 쌍을 넣으면 음별 판정(정답, 리듬만 맞음, 놓침)과 추가된 음, 점수가 나온다. 조옮김한 답도 같은 점수다. |
| 5 | `quiz-session` | 청음 테스트 진행 | full | `playlist-play`, `quiz-grading` | 휴대폰에서 `/p/:id/quiz` 를 열면 첫 음이 찍힌 빈 악보와 패드가 보인다. 재생을 듣고 패드로 입력해 제출하면 정답과 내 답이 겹친 악보와 점수가 보이고, 다음 문제로 넘어간다. |
| 6 | `quiz-result` | 세션 결과와 다시 풀기 | full | `quiz-session` | 마지막 문제를 내면 문제별 점수와 평균이 보이고, "틀린 문제만 다시 풀기"를 누르면 100점이 아닌 문제만 다시 나온다. |
| 7 | `mobile-audio` | 휴대폰 오디오 보강 | light | 없음 | iPhone 무음 모드에서도 재생되거나 안내 문구가 뜬다. 테스트 화면에서 화면이 꺼지지 않는다. 실기기 확인 항목으로 끝난다. |

의존 그래프:

```
playlist-schema → playlist-build → playlist-play ─┐
quiz-grading ─────────────────────────────────────┴→ quiz-session → quiz-result
mobile-audio (독립, quiz-session 전에 끝내는 것을 권장)
```

`quiz-grading` 과 `mobile-audio` 는 재생목록과 무관해서 먼저 또는 병렬로 진행할 수 있다.

## 10. 열린 질문

**Q1. 테스트 형식**
- 추천: 받아쓰기(3.1 A)만 첫 버전에 넣는다.
- 고르기를 함께 넣으면 기능이 하나 늘고 문제 진행 화면이 모드 분기를 가져야 한다.

**Q2. 첫 음 힌트**
- 추천: 항상 제공한다.
- 끄는 옵션을 두면 절대음감 테스트까지 되지만, 상대 음정 채점과 섞여 결과 해석이 어려워진다.

**Q3. 음 길이 채점**
- 추천: 첫 버전은 시작 위치와 피치만 채점한다.
- 예를 들어 정답이 4분음표(16분 4칸)인데 8분음표(2칸)로 입력하면, 추천안에서는 정답이고 길이까지 보면 오답이다.

**Q4. 릭이 지워졌을 때**
- 추천: 재생목록에서도 빠진다.
- 다른 안은 담을 때 `blob` 을 복사해 두는 것이다. 지워진 릭도 계속 풀 수 있지만, 작성자가 지운 릭이 남에게 계속 노출된다.

**Q5. 비로그인 테스트**
- 추천: 링크만 있으면 로그인 없이 테스트할 수 있다.
- 기록을 저장하지 않으니 로그인을 요구할 이유가 없고, 공유 링크로 들어오기도 쉽다.

**Q6. 앱 위치**
- 추천: 지금 Lick Share 앱 안에 둔다 (같은 리포, 같은 배포).
- 별도 앱으로 나누면 코덱, 플레이어, 패드를 패키지로 떼어내야 해서 선행 작업이 크게 늘어난다.
